# Jetvam repository guidance

Before changing business behavior, read `docs/architecture/jetvam-business-context.md`.

- Treat the manual and customer-journey video as descriptions of the current production journey.
- Treat the SRS as target-state roadmap requirements, not proof that a capability already exists.
- Preserve the distinction between current behavior and future requirements in code, migrations, and documentation.
- Authentication and authorization changes must follow `docs/security/frontend-authentication.md`.
- Every protected service operation must check both an appropriate role and a granular permission. Ownership checks such as `self` or merchant scope remain business-layer responsibilities and must not be replaced by role checks alone.
- All calls to external systems must follow `docs/architecture/external-integration-guidelines.md`: `jetvam-module-integration` contains only generic routing, HTTP, authentication, TLS/mTLS, failover and runtime provider configuration. Capability contracts, commands, results, codes and provider protocol adapters belong to the owning business module. Integration must never contain business capabilities such as Shahkar or SMS and must never depend on consumers.
- `jetvam-module-inquiry` owns applicant inquiry capabilities, including mobile ownership/Shahkar, bad cheque and credit rating. Identity, Assessment and future workflows consume its provider-neutral `InquiryService`; they must not own duplicate inquiry adapters or provider contracts.
- Never perform external network I/O while a database transaction is open. Split the workflow into short database phases around the external call and make the completion phase idempotent or concurrency-safe.
- In Product language, a `Product` is a commercial family and a `Plan` is the offer selected by the customer. Inquiry, guarantee, collateral and fee rules are configured per Plan; do not hardcode current-journey rules globally. Use stable domain codes across module boundaries so Product does not depend on Assessment, Guarantee or provider implementations.
- Product declares uniquely prioritized Plan controls but never executes them. An Inquiry definition is technical configuration behind at least one enabled Control, never an independently executable application requirement. Assessment evaluates age locally and obtains credit-rating or bad-cheque facts from Inquiry only when the current Control requires them.
- Origination owns the loan-application state machine and snapshots every enabled Control with its initial status when the application is created. Controls execute in strict priority order; the first failure cancels later Controls. Inquiry-backed Controls submit consumer-neutral requests and update themselves from an idempotent completion callback.
- Inquiry owns durable request execution, provider affinity and tracking, retries, terminal results and callback delivery. It must never depend on a consumer module. Callback transports implement `InquiryCallbackTransport`; `SPRING_BEAN` is the in-process transport and future MQ or webhook transports must be added without changing Inquiry's consumer-neutral workflow.
- Identity owns reusable customer personal and employment profile data in typed relational fields. Origination stores only the profile revisions consumed by an application and must reuse completed profile sections in later applications.
- Inquiry requests are durable asynchronous tasks. Submit and poll phases must be separated by persisted provider/tracking identifiers; polling a multi-step provider must return to the provider that accepted the original request. Completion callbacks use at-least-once delivery, so every consumer handler must be idempotent.
- Payment owns fee obligations and payment attempts. Origination activates Inquiry fees only when their prioritized Control becomes current, activates final application fees only after every Control passes, and cancels unpaid downstream fees on eligibility failure. Customers must never be able to mark their own payments successful.
- Keep module packages shallow and cohesive (`api`, `model`, `repository`, `service`, plus a capability-specific package only when needed). Prefer one narrow application service boundary and grouped nested request/view records over many single-record files.
- Product administration endpoints require both a system role and a product configuration permission. Customer/merchant catalog reads also require both an allowed role and `product:catalog:read`; downstream ownership and application eligibility remain business checks.
- Every top-level Java type must have class-level JavaDoc. Put its summary and description before the block tags, then include `@author reza jamshidi` and an `@since M/d/yyyy` value matching the type's creation date. JavaDoc has no standard `@description` tag; the leading paragraph is the rendered description.
